# Архитектура GiftOS

## Границы MVP

GiftOS — социальная платформа желаний и сборов. Главная цепочка MVP:

`желание → сбор → переход по ссылке → поддержка + сообщение → обсуждение → подписка → новое желание`.

В первой поставке нет Stars, стримов, маркетплейса, рекламного кабинета и свободного оборота внутренней валюты. Они не должны появляться в доменной модели как «временные» обходные сущности.

## Технологии

| Слой           | Решение                                      | Зона ответственности                               |
| -------------- | -------------------------------------------- | -------------------------------------------------- |
| Web / PWA      | Next.js 15, App Router, TypeScript           | Интерфейс, SEO-страницы сборов, серверные маршруты |
| UI             | Tailwind CSS + shadcn-совместимые компоненты | Единый интерфейс и доступность                     |
| Auth           | Supabase Auth                                | Magic link по email и OTP по телефону              |
| Данные         | Supabase Postgres + RLS                      | Доменная модель и авторизация на уровне БД         |
| Реальное время | Supabase Realtime                            | Чат сбора и уведомления                            |
| Файлы          | Supabase Storage                             | Аватары и изображения, доступ через signed URL     |
| Платежи        | Адаптер внешнего партнёра                    | Создание платежа, верификация webhook, возвраты    |

## Структура кода

```text
src/
  app/                  # Маршруты Next.js и серверные обработчики
  components/           # Общие UI и продуктовые компоненты
  lib/
    supabase/           # browser/server/admin Supabase clients
    payments/           # будет добавлен PaymentProvider adapter
    services/           # доменные сценарии, а не запросы из компонентов
  types/                # общие доменные типы
supabase/
  migrations/           # единственный источник структуры БД
  config.toml           # локальная конфигурация Supabase CLI
docs/                   # решения по архитектуре и продукту
```

## Ключевые доменные сущности

- `profiles`, `profile_interests` — публичная личность и интересы;
- `wishes` — желание существует само по себе и может стать основой сбора;
- `fundraisers` — центральный социальный объект;
- `fundraiser_supports` — внутренний журнал попыток поддержки, которым управляет webhook;
- `fundraiser_comments` — чат/обсуждение, поддержка может создать связанное сообщение;
- `user_follows`, `fundraiser_follows` — социальный граф и подписки;
- `conversations`, `conversation_members`, `messages` — фундамент личных сообщений;
- `reports`, `blocks`, `moderation_actions` — безопасность и модерация;
- `referral_codes`, `referrals`, `referral_events` — отложенная и проверяемая реферальная система.

Суммы хранятся как целые в минимальной единице валюты (`amount_minor`), а не как `float`: 2 000 ₽ = `200000` для RUB.

## Видимость

| Режим                    | Поведение                                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `public`                 | Может попасть в общую ленту, каталог и рекомендации.                                                                            |
| `unlisted` («по ссылке») | Не попадает в публичные view/ленты. Ссылка является bearer-идентификатором, поэтому slug должен быть длинным и непредсказуемым. |
| `private`                | Доступен автору, модератору и принятым приглашённым участникам.                                                                 |

`unlisted` не является криптографической защитой. Для действительно ограниченного круга используется `private` + `fundraiser_members`.

## Безопасность

1. Все пользовательские таблицы защищены RLS. Проверка интерфейса никогда не считается защитой.
2. Сырой `fundraiser_supports` не читается публично. Для ленты используется безопасный view `fundraiser_support_activity`, скрывающий сумму или личность по настройке пользователя.
3. Браузер не имеет политики `insert/update` на поддержках. Изменить платежный статус может только server-side код после проверки webhook провайдера.
4. Медиа-бакеты приватны. Signed URL выдаётся серверным сервисом после проверки прав на профиль/желание/сбор.
5. `SUPABASE_SERVICE_ROLE_KEY` используется только в server-only модулях и никогда не имеет префикса `NEXT_PUBLIC_`.
6. Реферальные события — лишь факт активности. Одобрение награды выполняет фоновый/административный сценарий после hold-периода и антифрод-проверки.

## Платёжный адаптер

Перед подключением конкретного провайдера в `src/lib/payments` создаётся интерфейс:

```ts
interface PaymentProvider {
  createSupport(input: CreateSupportInput): Promise<CheckoutSession>;
  verifyWebhook(request: Request): Promise<PaymentEvent>;
  createRefund(input: RefundInput): Promise<RefundResult>;
}
```

Webhook обязан быть идемпотентным по `provider + provider_payment_id`, проверить подпись провайдера и только затем поменять `support_status`. Триггер БД пересчитает прогресс сбора из подтверждённых поддержек. Нельзя принимать деньги на счёт приложения и самостоятельно распределять их между пользователями без согласованной юридической и платёжной модели.

## Реализация ближайших срезов

1. Подключить Supabase и применить миграции.
2. Сгенерировать database types: `supabase gen types typescript ... > src/types/database.ts`.
3. Собрать onboarding и настройки профиля.
4. Реализовать CRUD желаний, затем публикацию и просмотр сборов.
5. Добавить payment adapter в тестовом режиме, webhook и комментарий из подтверждённой поддержки.
6. Подключить Realtime только к комментариям и уведомлениям, затем добавить ленту и подписки.

# Staged QA: self-hosted city loop

**Статус:** tooling и сценарии подготовлены; фактический прогон на self-hosted
Supabase ещё не выполнялся, потому что production/local контур и синтетические
аккаунты пока не развёрнуты.

Цель этого этапа — проверить не отдельные страницы, а весь безопасный путь:

```text
auth → onboarding → Свои / город → люди → профиль → место → story/live/event
→ личный диалог → Активность → возврат в город
```

В прогоне используются только тестовые аккаунты и синтетические медиа. Не
использовать настоящие имена, телефоны, фотографии, платежи или production ПДн.

## 1. Что запускается до стенда

```bash
npm run qa:migrations
npm run lint
npm run typecheck
npm run build
```

`qa:migrations` проверяет имя, порядок, уникальность версий и непустые SQL-файлы
в `supabase/migrations`. Он не применяет миграции и не меняет базу.

## 2. Preflight self-hosted контура

После заполнения **`.env.local` реальными ключами self-hosted контура**:

```bash
npm run qa:selfhosted
```

Проверка не печатает ключи. Она:

- отклоняет placeholder-значения и endpoint Supabase Cloud;
- проверяет валидность URL;
- делает два read-only запроса: health Auth и чтение публичного справочника
  `cities`;
- сообщает отдельно, если LiveKit пока не настроен.

Для локальной проверки самого скрипта без сети:

```bash
NEXT_PUBLIC_SUPABASE_URL=https://supabase.qa.internal \
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=qa-publishable-key \
SUPABASE_SERVICE_ROLE_KEY=qa-service-role-key \
NEXT_PUBLIC_APP_URL=https://app.qa.internal \
node scripts/qa/selfhosted-preflight.mjs --skip-network
```

Эти значения демонстрационные: скрипт не подключается к ним с
`--skip-network`.

## 3. Синтетические роли стенда

| Роль         | Назначение                             | Городская видимость                          |
| ------------ | -------------------------------------- | -------------------------------------------- |
| `qa_host`    | создаёт место, событие, story/live     | public + show_city                           |
| `qa_creator` | local-витрина и публичная история      | public + show_city + listed                  |
| `qa_viewer`  | проходит onboarding и подписывается    | city chosen, show_city off в первом сценарии |
| `qa_public`  | проверяет публичные City Moments       | public + show_city + moments on              |
| `qa_private` | проверка отсутствия в выдаче           | private или show_city off                    |
| `qa_blocked` | проверка блокировок и личных сообщений | отдельный synthetic account                  |

Пароли, адреса и медиа генерируются для контура и удаляются после QA.

## 4. Сценарии приёмки

### A. Первый вход и свой город

1. `qa_viewer` завершает onboarding с городом Будённовск и выключенным
   `show_city`.
2. Проверить: пользователь видит `Свои`, City Now, людей и события своего
   города.
3. Проверить: `qa_viewer` не появляется в `/people`, City Pulse, рейтингах и
   local-витрине для других.
4. Включить `show_city` в Settings и обновить выдачи; профиль становится
   доступен только как публичный городской профиль.

### B. Люди → профиль → публичная сцена

1. `qa_creator` включает local-витрину и создаёт story, live или событие.
2. `qa_viewer` открывает `/people?scope=city`, затем профиль автора.
3. Проверить: карточка ведёт в реальную story/live/event, а не показывает
   вымышленный контекст.
4. Подписаться и убедиться, что автор появляется в «Своих».

### C. Место, моменты и согласие

1. `qa_host` создаёт публичное место; `qa_public` присоединяется.
2. С включёнными consent у всех участников создать разрешённый public moment.
3. Проверить появление в City Pulse и вкладке «В городе» Активности.
4. Выключить `share_city_moments` у одного участника и повторить действие.
5. Проверить: основное действие выполняется, но публичный момент не создаётся.

### D. Приватный слой

1. Создать личный диалог между `qa_viewer` и `qa_creator`.
2. Проверить, что его нет в City Pulse, рейтингах и публичных профилях.
3. Выключить личные сообщения у получателя; попытка начать новый диалог должна
   быть отклонена существующими правилами.
4. Проверить блокировку: публичные и личные переходы не обходят block rules.

### E. События и репутация

1. `qa_host` создаёт городское событие, привязав действующее место.
2. `qa_viewer` добровольно присоединяется и получает актуальный экран события.
3. Проверить `/city/rankings`: реальные публичные позиции, без raw score и без
   заявлений о несуществующей исторической дельте.
4. Проверить: бонусы/VIP/продвижение не создают позицию напрямую.

### F. Return loop

1. Создать одно личное уведомление и одно безопасное публичное городское
   изменение.
2. Открыть `/notifications`: «У тебя» содержит только личное, «В городе» —
   только safe City Pulse.
3. Проверить переходы обратно в конкретные профиль, место, story/live или
   событие.

## 5. Stop conditions

Не запускать закрытый beta/production, если обнаружено хотя бы одно:

- private/show_city-off профиль виден в публичной городской выдаче;
- DM, платный запрос, приватный сбор или неconsented подарок попал в City Pulse;
- действие не проходит из-за сбоя best-effort City Moment записи;
- City Moment сохраняется при выключенном consent участника;
- город виден пользователю только при публичном `show_city`;
- production endpoint указывает на Supabase Cloud;
- денежный flow перестал быть test-mode или обходит авторское согласие.

## 6. Результат прогона

В `docs/КОНТЕКСТ_ИИ.md` фиксируются только агрегированные результаты:
дата, версия миграций, список пройденных сценариев, блокеры и решение о
следующей стадии. Не записывать ключи, настоящие данные аккаунтов, IP, номера
телефонов или платежную информацию.

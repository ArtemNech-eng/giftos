# Production-инфраструктура GiftOS в РФ

**Статус:** принятое архитектурное решение.

**Дата:** 5 августа 2026.

## Решение

Production-версия GiftOS использует **self-hosted Supabase** в дата-центре / облаке с физическим размещением инфраструктуры в Российской Федерации. Supabase Cloud не используется как production-хранилище или сервис первичного сбора персональных данных российских пользователей.

Технологический стек не меняется: приложение продолжает работать с совместимыми Supabase Auth, Postgres, Storage и Realtime API. Поэтому клиентский код, RLS-политики и миграции из этого репозитория сохраняются.

> Это техническое решение, а не юридическое заключение. До публичного запуска оператору необходимо подтвердить модель обработки персональных данных, трансграничные процессы и документы с профильным юристом.

## Целевая топология

```text
Пользователь
  │
  ├── HTTPS / домен giftos.ru
  ▼
Next.js / PWA (российская инфраструктура)
  │
  ├── Auth / API / Realtime
  ├── PostgreSQL + резервные копии
  └── Object Storage: аватары и изображения
       ▼
Self-hosted Supabase (российская инфраструктура)
  │
  ├── российский email/SMS-провайдер
  └── платёжный партнёр (после отдельного согласования)
```

## Что относится к локализуемому контуру

В российском контуре должны находиться как минимум:

- основная PostgreSQL-база, включая `auth.users`, профили, сообщения, желания, сборы и жалобы;
- Storage с аватарами, изображениями желаний и обложками сборов;
- резервные копии, WAL-архивы и реплики базы;
- сервис авторизации, сессии, логи, очереди и уведомления, если в них есть персональные данные;
- Next.js-сервер и серверные обработчики форм / webhook;
- аналитика и мониторинг, если они получают IP-адреса, идентификаторы или другие персональные данные.

Сторонние сервисы нельзя подключать по умолчанию. Для каждого email-, SMS-, аналитического, crash-reporting-, CDN- или CRM-поставщика требуется отдельно проверить маршрут данных и условия договора.

## Среды

| Среда                | Инфраструктура                          | Данные                               |
| -------------------- | --------------------------------------- | ------------------------------------ |
| Локальная разработка | `supabase start` на машине разработчика | Только синтетические тестовые данные |
| Staging              | Изолированная российская инфраструктура | Обезличенные / тестовые данные       |
| Production           | Self-hosted Supabase в РФ               | Реальные пользовательские данные     |

В development и staging запрещено использовать реальные данные пользователей без отдельной необходимости, оснований и мер защиты.

## Минимальные требования к production

1. Письменно подтвердить у провайдера физическое размещение compute, дисков, резервных копий и реплик в РФ.
2. Развернуть Supabase Auth, Postgres, Storage и Realtime в приватной сети; наружу опубликовать только нужные HTTPS-маршруты через reverse proxy / WAF.
3. Хранить `SUPABASE_SERVICE_ROLE_KEY`, ключи SMTP/SMS и ключи платежей только в secrets manager или защищённых переменных окружения.
4. Включить TLS, шифрование дисков и резервных копий, ротацию секретов, контроль доступа и аудит административных действий.
5. Проверить, что backup, error-tracking, мониторинг, почтовая доставка и метрики не пересылают персональные данные в иностранные сервисы без согласованной модели.
6. Настроить регулярное тестовое восстановление базы и Storage из резервных копий.

## Конфигурация приложения

Приложение не зависит от Supabase Cloud. В production достаточно указать endpoint self-hosted развертывания:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://supabase.giftos.ru
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<publishable-key>
SUPABASE_SERVICE_ROLE_KEY=<server-only-secret>
NEXT_PUBLIC_APP_URL=https://giftos.ru
```

`SUPABASE_SERVICE_ROLE_KEY` используется только в server-only коде для выдачи signed URL и доверенных webhook-операций. Он никогда не передаётся браузеру.

## Порядок запуска

1. Выбрать российского инфраструктурного провайдера и подтвердить размещение всех указанных компонентов в РФ.
2. Развернуть self-hosted Supabase, настроить домен, TLS, SMTP/SMS и резервное копирование.
3. Применить миграции из `supabase/migrations` через защищённый CI/CD-канал к production PostgreSQL.
4. Настроить переменные окружения GiftOS в secrets manager.
5. Прогнать staging-проверку: регистрация, загрузка изображения, создание желания, создание сбора, RLS и восстановление из backup.
6. Провести юридическую и ИБ-проверку перед приёмом реальных пользовательских данных.
